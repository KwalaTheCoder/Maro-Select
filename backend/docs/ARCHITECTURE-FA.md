# معماری و تصمیم‌ها

## مرز دو خروجی

پیش‌نمایش آنلاین فقط HTML/CSS/JS است؛ محصول و سبد نمونه را در مرورگر نگه می‌دارد، پنل آن احراز هویت واقعی ندارد، اطلاعات مهمان به سرور ارسال نمی‌شود و پرداخت/سفارش واقعی ایجاد نمی‌کند. پیام دمو در رابط نمایش داده می‌شود. میزبانی پیش‌نمایش خارجی است و نمایندهٔ مقاومت نسخهٔ ایرانی در قطع اینترنت نیست.

بستهٔ Laravel جداگانه برای هاست ایران است. فونت Noto Kufi Arabic با مجوز موجود در `public/assets/FONT-LICENSE.txt`، عکس‌ها و فایل‌های frontend محلی‌اند. کد خصوصی و DB بیرون public هستند. هیچ وابستگی اجرایی به npm، AI، Google Fonts، Supabase، Firebase، نقشه یا کپچای خارجی وجود ندارد. تنها اتصال بیرونی لازم برای پرداخت، سرویس درگاه داخلی است.

## داده

پول bigint ریال است؛ تبدیل تومان با ضریب ۱۰ و بدون float. کاربران جدول users با is_admin و TOTP اختیاری هستند. Product، Variant، Image و Category جدا هستند. سفارش snapshot نام، SKU، تنوع، تعداد، قیمت و ارسال دارد. رزرو موجودی، تلاش پرداخت، گردش موجودی، ارسال و audit جدا هستند. Cart و DiscountCode جدول دارند، اما سبد فعلی مرورگری و کد تخفیف غیرفعال است؛ امکانات غیرعملی در UI وعده داده نشده‌اند.

## پرداخت و موجودی

quote از قیمت‌های DB ساخته و با HMAC به همان جلسه متصل می‌شود. تغییر قیمت/ارسال بین بررسی و ثبت، تأیید دوباره می‌خواهد. start در transaction، تنوع‌ها را با ترتیب شناسه قفل می‌کند، موجودی آزاد را از موجودی فیزیکی منهای رزروهای فعال می‌سنجد و رزرو ۱۵ دقیقه‌ای ایجاد می‌کند. نتیجهٔ شبکه خارج از transaction درخواست می‌شود. callback فقط authority را برای یافتن تلاش می‌گیرد؛ مبلغ از DB به Verify ارسال می‌شود. تکرار callback با قفل سفارش و تلاش پرداخت دوباره موجودی کم نمی‌کند. unique event_key مانع گردش تکراری است.

پرداخت دیرهنگام، موجودی آزاد از سایر رزروها را دوباره بررسی می‌کند. در کمبود، paid_exception ثبت می‌شود و موجودی منفی نمی‌شود. retry فقط برای failed/disabled مجاز است؛ review/pending/paid دوباره به پرداخت هدایت نمی‌شوند. retry تلاش جدید برای همان سفارش ایجاد می‌کند. پس از تغییر قیمت، سفارش باید مجدداً بررسی شود. دو پرداخت تأییدشده برای یک سفارش نیازمند رسیدگی‌اند؛ اجرای خودکار استرداد وجه در این نسخه نیست.

قطع فرآیند بین درخواست درگاه و ذخیرهٔ authority یک استثنای عملیاتی است: ممکن است نیاز به تطبیق دستی در پنل پذیرنده باشد. به آن سفارش نباید بدون بررسی، امکان پرداخت مجدد داد. reconciliation خودکار فقط authorityهای ذخیره‌شده را بررسی می‌کند.

## امنیت

CSRF وب Laravel، Hash رمز، محدودیت ورود و tracking، کنترل مدیر، query builder، escape خروجی، CSP، no-store اطلاعات حساس و توکن پیگیری ۲۵۶بیتی وجود دارند. URL پیگیری حاوی موبایل، آدرس یا توکن نیست؛ توکن با POST فرستاده می‌شود. خروجی tracking آدرس و موبایل را افشا نمی‌کند. فایل‌ها MIME و dimensions بررسی و با GD به WebP بازرمزگذاری می‌شوند؛ اصل فایل خصوصی است. دسترسی وب به اصل فایل وجود ندارد.

## محدودیت‌های صریح نسخهٔ اول

- آزمون واقعی هم‌زمانی MySQL، درگاه، اینترنت داخلی، هاست و SSL هنوز انجام نشده.
- پرفروش واقعی، کد تخفیف، پیامک و نسخهٔ حساب‌دار سبد فعال نیستند؛ منتخب مدیر جای پرفروش نمایش داده می‌شود.
- اندازه‌بندی/رنگ محصول، اطلاعات قانونی و تماس فعلی دمو یا خالی‌اند؛ ادعای کالا ساخته نشده است.
- UI مدیریت عکس، ترتیب و چندآپلود دارد؛ حذف عکس و سیاست خودکار پاکسازی originals پیاده نشده و باید با فضای هاست تنظیم شود.
- داشبورد ساده است؛ گردش مالی استرداد، اصلاح امن آدرس بعد از خرید، بازیابی توکن از طریق پشتیبانی و پنل تاریخچهٔ audit به‌صورت کامل UI ندارند. لاگ‌های سرور موجودند؛ پرداخت‌شده‌کردن دستی سفارش در UI اصلاً مجاز نیست.
- آداپتور درگاه نیازمند تست پذیرنده است. هیچ اتصال به هاست/دامنهٔ مالک بدون دسترسی انجام نشده.
- SEO محصول مسیر واقعی، canonical، metadata و sitemap دارد؛ صفحات تعاملی هنوز hash route هستند. صفحهٔ اصلی بیشتر با JS رندر می‌شود و برای سئوی کامل مرحلهٔ بعد SSR محتوای عمومی لازم است.
- بکاپ محلی رمزگذاری می‌شود؛ کپی مستقل و هشدار عملیاتی باید روی هاست وصل شوند. اندازهٔ بزرگ بکاپ به حافظهٔ بیشتری نیاز دارد.

این‌ها تعهد اجراشده تلقی نمی‌شوند؛ پیش از پذیرش فروش واقعی باید به‌طور مشخص تعیین تکلیف شوند.
